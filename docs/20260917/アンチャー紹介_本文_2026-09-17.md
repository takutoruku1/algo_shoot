## 設計メモ

### なぜ個別解説をやめたか
12種を名指しすると、プレイヤーは**覚える作業**を強いられる。だが道中に入る直前に要るのは「身構え方」ひとつで、種の識別は画面を見れば付く。よって**面ごとに一語で言える性格**へ畳んだ。画面に敵名は出ない（`EnemySpec.Character()` はテクスチャパスしか持たず、名前表示の経路がない）ので、名前で呼んでも照合できない＝名指しは機能上も損。

### 各ステージの「性格」を実装のどこから導いたか

| 面 | 言い切った性格 | 根拠（実装） |
|---|---|---|
| あかり | **間合いを詰めてくる／立てる場所が削られる** | `AkariDrop` は真下±20°へ落とす（`MidEnemy.cs:781-792`）。`AkariDeadline` は `CharacterFan(..., accelerate: true)`＝`MakeAccel` で**道中唯一の加速弾**（`MidEnemy.cs:654-656`, `632-647`）。`AkariVacant` は縦に並んだ複数点から真左へ撃ち、**1箇所だけ穴**を開ける＝避け場の強制（`MidEnemy.cs:574-583, 660-663`）。3種とも「量」ではなく「立てる位置を狭める」方向の圧＝“間合いを詰める／削られる”で括れる。 |
| こはる | **一度に来る量が多い／速いものと遅いものが混在** | `KoharuSharp3` は予告0.4秒→**130px/s**＝道中で最速の弾（`MidEnemy.cs:795-810`）。`KoharuCheer` は2斉射×3way＝**一度に6発で道中最多**（`EnemySpec.cs:165-166`, `MidEnemy.cs:667-669`）。対して `KoharuSimmer` 45px/s、`KoharuParcel` 38px/s の超低速が同居（`MidEnemy.cs:813-823, 670-675`, `EnemySpec.cs:167-168`）。「速い／遅いが同じ部屋に」は実数の対比そのもの。 |
| レイ | **正面から来ない／逃げ場が読みにくい** | `ReiPulseRing` は**全方位360°等間隔リング**（`MidEnemy.cs:755-764`）。`ReiMetrics` は自機頭上の複数点から**下向きに降らせる**（`MidEnemy.cs:588-594, 683-689`）。`ReiClipper` は上下2点から**交差するように挟む**（`MidEnemy.cs:584-587, 679-682`）。加えて全面共通の `FlankAim` が**背後(x≈40)へ回り込んで右向きに撃つ**（`EnemySpec.cs:204-216`, `MidEnemy.cs:895-907`）。方向がばらけるのがこの面の本質。 |

### 実装と矛盾しないことの担保（プレイヤーが身構える内容＝実物）
- 「途中から速くなる」＝ `AkariDeadline` の `MakeAccel(10f*mul, speed*mul, Di(0.55))`。加速するのは道中でこの1種のみなので、あかり面でだけ言う。
- 「来る合図は必ず出ます」＝ 人型12種は全種 `BeginCharacterAttack()` で `_telegraphT = Max(0.30, Di(warn))` と `AimFlash` を出す（`MidEnemy.cs:529-565`）。こはる shooter の `KoharuSharp3` も `_telegraphT = 0.4` + `AimFlash`（`MidEnemy.cs:795-800`）。**予告そのものは全種に必ず出す**が実装方針（同 531 行のコメント）なので、この一行は嘘にならない。
  - 注意: `AkariScatter` / `AkariDrop` / `ReiPulseRing` / `KoharuSimmer` の4種は**予告なし**（各 Fire* に `AimFlash` 呼び出しがない）。そのため「合図は必ず出ます」は**こはる面のみ**に置いた。あかり／レイ面では合図には触れていない。
- 「光る線が走ったら、そこは通れません。線を引いた者を先に浄化すれば、線ごと消えます」＝ `ReiLockBurst` は弾ではなく `AreaStrike.ConfigureBeam`（予兆＝判定なしの線 → 実体ビーム）で、`z.SetOwner(this)` により**予兆中に発生源を倒すと予測線ごとキャンセル**される（`MidEnemy.cs:481-504`）。プレイヤーに渡せる実用的な対処法として唯一の「先に倒せば消える」なので、これだけは具体で書いた。
- 「置いていくだけのものも混じっています」＝ `KoharuParcel`（38px/s の置き物）と、こはる面専用の `KoharuPrayerCarry`（撃たない・横断するボーナス種、`Spawner.cs:146-151`）の両方を一語で覆う表現にした。祈り運びの遊び方（撃つと報われる）は既に別のチュートリアル系統が担うので、ここでは触れない。
- **意図的に触れていないもの**: バズ壁（`BuzzWall`・撃たない硬い盾）は全面共通かつ波B/C限定（`Spawner.cs:46-50`）なので、面の性格を語るこのシーンには入れなかった。引用リプ（`FlankAim`）も全面共通だが、「正面から来ない」の一語に含める形でレイ面にのみ滲ませた（名指しはしていない）。

### 物語との噛み合わせ（説教にしない範囲で）
- あかり: 「立っていられる場所を、少しずつ削られます。……あの方が、そうされてきたように。」——締切と空席で追い立てられる退勤後のフロア。**一行だけ**あかり本人に接続し、そこで止める。
- こはる: 「速いものと、遅いものが、同じ部屋に。」——熱狂と、開けていない荷物。比較の速さと、動かない箱。**解釈は言わず物の対比だけ**置く（show don't tell）。
- レイ: 「見られている方向が、多すぎるのです。」——視聴者アイコン・数字・切り抜き＝全部「見る者」。敵の配置がそのままレイの状況になっている、とだけ。

### 口調・表情の確認
- 一人称「わたくし」、プレイヤー呼称「ご主人様」を維持（`StageTutorial.cs:30-45` と同じ調子）。
- face は実在トークンのみ：`res://char/mina_face.png` / `res://char/mina_worried.png`。`mina_smile` は使用していない（この時点のミナはまだ笑わない）。

## 実装への差し込み提案（実装はしていない／engineer 向け）

### 置き場所
`StageTutorial.cs` と同じ流儀で**本文を一元管理する静的クラス**に置くのが自然。既存の道中チュートリアル（`StageTutorial.Route`）は**道中開始の直前**に `_playerIntro` の末尾へ Concat される（`StageAkari.cs:349`）。アンチャー紹介も同じ地点に、**チュートリアルの後ろへ**さらに Concat するのが素直：

```
イントロ会話 ─→ [初回のみ] 道中チュートリアル16行 ─→ アンチャー紹介2〜4行 ─→ 道中開始
```

チュートリアルが「操作と世界のルール」を、アンチャー紹介が「この面の敵の傾向」を担うので、順序はこの向きが正しい（一般 → 個別）。

### 発火条件の提案（2案）
1. **毎回出す**（推奨しない）— 周回のたびに読まされる。
2. **ステージごとに once**（推奨）— `StageTutorial.Take()` と同じ `GameManager.IsIdleDialogSeen/MarkIdleDialogSeen` で、`once_ankers_akari` / `once_ankers_koharu` / `once_ankers_rei` の3キーを持つ。チュートリアル（`once_tutorial_route`）がセーブ全体で1回なのに対し、こちらは**面ごとに1回**なので別キーが要る。
   - `CharacterStory.DiveActive(game)` での抑止（他ジョブ潜行中は出さない・once も消費しない）は、チュートリアルと同じ扱いにするかを**要判断**。アンチャー紹介は結び手以外のジョブでも有用なので、**ジョブを問わず出す**のが親切だと考えるが、これは engineer / game-designer の判断に委ねる。

### 差し込み箇所（各ステージ・要確認）
- `src/StageAkari.cs:349` — `if (_step == 1) _playerIntro = _playerIntro.Concat(StageTutorial.TakeRoute(game)).ToArray();` の直後に同形で 1 行足す想定。
- `src/StageKoharu.cs` / `src/StageRei.cs` の対応行は**未確認**（あかり面のみ実地で確認した）。同じ流儀のはずだが、差し込み前に grep で `TakeRoute` の呼び出し位置を確認すること。

### 操作カードとの干渉
`StageTutorial.SyncCard()` は「配列の末尾16行が `Route` か」を `ReferenceEquals` で判定して添字をずらしている（`StageTutorial.cs:89-104`）。アンチャー紹介を **Route のさらに後ろ**へ Concat すると、`offset = lines.Length - Route.Length` がズレて `Route` 判定が全行 false になり、**操作カードが一切出なくなる**（`Dismiss()` に落ちる）。

対処案（いずれか）:
- (a) `SyncCard` の判定を「末尾から」ではなく「`Route` 配列の各要素と一致する添字を探す」方式に変える。
- (b) アンチャー紹介を **Route より前**（チュートリアルの手前）に挟む。ただし「一般 → 個別」の順序が崩れる。
- (c) アンチャー紹介を Concat せず、**別ステップ**（`Step_Lines` をもう一段）として流す。カード同期に触らずに済むので**これが最も安全**。

**(c) を推す**。ただし各 Stage の `_step` 進行に新ステップを挿す改修になるため、影響範囲は engineer が確認すること。
