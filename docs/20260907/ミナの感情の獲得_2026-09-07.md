# ミナの感情の獲得（2026-09-07 ユーザー確定）

ユーザー原文:

> 冒頭での MINA は寂しいとか悲しいとかつらいとか、そういった感情はなくて、実際に悲しい心に触れて、徐々に泣くことができる、笑うことのできる表情が増えていく、そんなキャラクターにしたい。

> 「——放っておけません。潜ります。」のセリフは最初のオープニングの MINA のイメージと合わない。

## 何が決まったか

**ミナは感情を持って生まれない。三人の心に触れることで、少しずつ獲得していく。** これが冒頭から結末までを貫くミナ自身の線になる。

- **冒頭のミナに感情語は無い**。寂しい・悲しい・つらい・放っておけない、は言わない。あるのは**観測と、処理の判断**だけ。
- 「放っておけません」は**感情による動機**なので冒頭に置けない。潜る理由は、**観測した事実の処理**として言う（例: 消えていない言葉がある。拾えるのは自分だけ。だから行く）。
- 三人の面を経るごとに、**使える表情が増える**。笑う・泣くは後半で初めて成立する。
- 終盤（FINAL・エピローグ）では感情を持った状態で喋れる。E5b の「拾えるところにいたい、と思います」は**願望＝感情**なので、そこまで来て初めて言える台詞になる。この順序は既に正しい。

## 実装との照らし合わせ（要調査）

- ミナの表情素材は `mina_face` / `mina_smile` / `mina_worried` / `mina_tears` / `mina_doubt` 等。**現状は冒頭から全部使えてしまう**。冒頭で `mina_smile` や `mina_tears` が出ていないかを洗い、出ていれば差し替える。
- 「使える表情が増える」を**仕組みとして持たせるか**（面のクリア数で解禁）、**台本側の運用だけで守るか**は判断が要る。仕組みにすると、台本の書き手が間違えても破綻しない。
- 冒頭の台詞から感情語を洗い出して置換する（`src/Prologue.cs` と `wiki/08_仮台本/04_冒頭台本_案C.md`）。

## 決定（2026-09-07 ユーザー・指揮官）

1. **仕組みにする**（表示側でクランプ）。運用だけでは既に約30箇所が違反しており、`DiffSelect` のように台本の外にある画面は運用で防げないため。
2. **順序は あかり後＝困る／こはる後＝笑う／レイ後＝泣く**。入れ替えない。
3. **こはる面の道中は案I（厳格）**。ユーザー決定。道中は無表情のままにし、改心の直後に初めて笑う。増える瞬間が一点に決まる。
4. `DiffSelect` の「底まで」に例外は作らない。未解禁なら worried に落ちる。

## 1. 解禁の順序 — 案のまま（あかり＝困る／こはる＝笑う／レイ＝泣く）

三面の内容から見て、この順で正しい。入れ替えない。

| 面 | 得るもの | なぜその面か |
|---|---|---|
| あかり | **困る**（worried が本物になる） | あかりの闇は「返事が来ない」。ミナは十二通を浴びて証人にはなれるが、憲法上**返事を代弁できない**。「拾ったのに、返せない」という処理不能の経験が、worried を「観測が引っかかった顔」から「どうにもできない顔」へ変える。困るは、何もできなかった側にだけ残るので、いちばん早く手に入る |

## 3. 仕組み化するか、運用で守るか — **仕組み化を推す**

### 危険の見積り

運用（書き手が守る）だけの場合、破綻する経路が**すでに3つ**ある:

1. **`DiffSelect` は進行度と無関係に全4段を並べる**。初回起動でカーソルを「底まで」へ動かすだけで `mina_tears` が出る。台本の運用では絶対に防げない（台本の外にある画面）。
2. **面の順番が可変**。ハブは解放済みの面へ自由に入れるうえ、`--stage` 系のデバッグ導線・中ボス/ボスからの再開もある。「レイの面だから tears は解禁済み」という前提が、実プレイの経路では保証されない。
3. **周回**。2周目はクリア済みだが、`Hub.ClearBacklog()` と `GameManager.MinaNamed=false`（`Prologue.cs:115`）が示すとおり、この作品は**周回でも冒頭を毎回同じ体験にする**方針で作られている。感情だけ持ち越すのか・リセットするのかは、台本の運用では表現できない（値が要る）。

上の A〜E で洗い出したとおり、**現時点で既に 30 箇所前後が違反している**。これは書き手の不注意ではなく、ルールが今日決まったからだが、同じことは今後も起きる（新しい小話・新しい面・新しい画面）。運用だけで守る前提は成り立たない。

### 実装の重さ — 軽い

推し案は **`Hud` の表示側で弾く（クランプ方式）**。台本側は今までどおり「その行で出したい表情」を書き、**表示の直前に、解禁されていない表情を一段落とす**。

```
mina_tears  → (tears 未解禁なら) mina_worried
mina_smile  → (smile 未解禁なら) mina_face
mina_worried→ (常に可。冒頭は「観測が引っかかった顔」として使う)
mina_face   → 常に可
```

- **1関数で済む**。`GameManager` に `EmotionTier` （0=無感情／1=困る／2=笑う／3=泣く。クリア済み面数から算出）を1本足し、`static string ClampMinaFace(string path)` を `UiKit` か `Hud` に置く。読み込み地点が `Hud`／`Prologue.DrawTalkSpeakers`／`DiffSelect`／`ShopTutorial.FaceTex` に分かれているので、**テクスチャをロードする4箇所でこの関数を通す**だけ。分岐は増えない。
- **台本を書き換えなくても破綻しなくなる**。上の A〜E の 30 箇所は、クランプを入れた時点で自動的に正しい顔になる（`StageAkari.cs:66` の `MSmile` は、あかり面ではまだ tier 0 なので `mina_face` で出る）。**ただし文字（感情語）はクランプできない**ので、★印の「嫌いじゃありません」「好きなので」「気に入りました」「放っておけません」だけは手で直す必要がある。
- **例外の逃げ道が要る**。`DiffSelect` の「底まで」は演出上 tears を出したい可能性がある（覚悟を問う顔）。クランプを通さない生パスの指定（例: `mina_tears!` のような接尾辞、または `ClampMinaFace` を通さない呼び出し）を1本だけ残す。ただし現状の推しは**例外を作らず、初回は worried に落とす**（「……覚悟は、できていますか。」は worried でも成立する。むしろ泣き顔で言われるより不穏で良い）。

### 弾く場所は表示側か台本側か

**表示側（`Hud`／各レンダラのロード地点）を推す。** 理由:

- 台本側で持つ（各行に「この表情は tier2 以降」と書く）と、書き手が毎行判断することになる＝運用と同じ危険が残る。
- 表示側なら**一箇所で全画面に効く**。`Prologue` は独自レンダラ、`Hud` は本編、`DiffSelect`／`ShopTutorial` は自前ロードと、経路が4つに割れているのが今の構造なので、「共通のロード関数を1本通す」形にしておくと、今後画面が増えても勝手に守られる。
- 副作用として**アセットの取り違えも防げる**（存在しない表情パスのフォールバック先を同じ関数に置ける）。

- 案a: `Hub` の会話も face 付きの3要素にする（影響範囲: `ReturnDialog`／`IdleDialogs`／`ReplyDialog`／`BurnDialog`／`SmallTalks`／`PinnedIdle`／`WithS15`／`StartDialogue`）。重い。
- 案b: 解禁の一行は**ハブではなく面のクリア直後**（`Clear` 配列）に置く。こちらは既に face 付きなので追加コストゼロ。**推しは案b**。

挿入位置（いずれも `Clear` 配列の末尾に追記。空の問いの後に置くと、問いへの無返答の直後に感情が出る形になって効く）:
