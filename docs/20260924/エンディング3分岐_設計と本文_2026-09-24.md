## 1. メーター【開き】の定義

### 1.1 何のメーターか

**名前: 【開き】**

本作の中核テーマは「下書き＝本音、投稿＝仮初。埋もれた本音を掘り起こす」。ならばメーターが測るべきは好感度ではなく、**そのボスが自分の下書きをどれだけ開いて見せているか**。

```
【開き】0.0 ── 閉じきっている。投稿しか出さない。本音は全部下書きのまま。
【開き】0.5 ── 半分開いている。言いかけて、止める。
【開き】1.0 ── 開いている。下書きのまま喋る。取り消さない。
```

- 「好感度」ではない。**ミナを好きかどうかを測っていない。** あかりが【開き】0.9 でも、それは「ミナを好き」ではなく「自分の本音を出せている」。
- 【濁】（`Contamination`）との違い: 【濁】は**ミナ**の状態、【開き】は**相手**の状態。方向が逆で、混同しない。
- ゲーム内での呼称も「【開き】」。ミナは数える人なので、数えられるものには名前がある。ただし**プレイヤーに数字は見せない**（§3）。

**命名の検証**: 既存の全角括弧系列——【濁】（汚染）／【散】（散った言葉）／【初】（最初に散らした語）／【終】（最後に送った語）。すべて漢字1字。【開】でもよいが、「ひらき」と読ませたいので**【開き】**を採る。`ChoiceEffects.cs` や `Final.cs:146` のコメントがこの記法を既に使っている。

### 1.2 ボスごとに3本。共通1本にしない理由

作者の指示が「**BOSSに**感情メーターを作って」なので、ボスごとに持たせる。設計上もこちらが正しい:

- 3人は**別アーキタイプ**（`maeda-pitfalls.md` P1）。あかり＝返事を待つ人／こはる＝嘘で明るくする人／レイ＝数字に見られている人。同じ1本で測ると3人が同型に潰れる。
- 共通1本だと「全体のやさしさポイント」になり、作者が避けたい無味乾燥な数値そのものになる。
- 3本あると、**「誰には開かせられて、誰には開かせられなかったか」**という差が出る。これが最後に効く（§5）。

```csharp
// 読み出し（ChoiceEffects.cs:63 の partial GameManager ブロックに生やす想定）
public float Openness(string boss);   // "akari" / "koharu" / "rei" → 0.0〜1.0
```

**永続化は不要。** 【開き】は `RecordChoice` で既に保存済みの `_chosenById` から**毎回その場で計算する**純関数。新しいセーブ項目をゼロ個足す。旧セーブは「該当 id が無い＝既定値」で素直に中庸へ落ちる（後方互換が自動で効く）。

```csharp
// 実体はこれだけ。状態を持たない＝リトライ・ロード・周回で破綻しない。
public float Openness(string boss) => boss switch
{
    "akari"  => Mathf.Clamp(0.5f + AkariDelta,  0f, 1f),
    "koharu" => Mathf.Clamp(0.5f + KoharuDelta, 0f, 1f),
    "rei"    => Mathf.Clamp(0.5f + ReiDelta,    0f, 1f),
    _ => 0.5f,
};
```

**既定は 0.5（半分開いている）。** 0 始まりにしない——何も選ばなかった人が最初から最悪の状態になるのは罰であって物語ではない。中庸から上下に振れる。

## 2. 何が【開き】を上げ下げするか（対応表）

### 2.1 設計の原則

- **「正解」を作らない。** どの選択肢も、開く方向か閉じる方向かのどちらかに倒れるだけで、**閉じる側が悪ではない**。閉じたボスは苛烈な弾幕で、開いたボスは静かな弾幕で、プレイヤーに違う顔を見せる。
- **（送らない）は一律で下げる**が、下げ幅は小さい。黙ることは罪ではない。ただし相手は開かない。
- **加算は各ボスにつき最大 ±0.5**（既定 0.5 からの振れ幅）。全部開く方向に振ると 1.0、全部閉じる方向だと 0.0。

### 2.3 【開き】の3段階（弾幕と台詞が切り替わる区切り）

連続値のままでは実装も演出も扱いにくいので、**3段に丸めて使う**。

```csharp
public enum Openness3 { Closed, Half, Open }   // 閉／半／開
public static Openness3 Band(float v) => v < 0.35f ? Closed : v < 0.70f ? Half : Open;
```

| 段 | 範囲 | 状態 |
|---|---|---|
| **閉** | 0.00 – 0.34 | 投稿しか出さない。本音は全部下書きのまま。 |
| **半** | 0.35 – 0.69 | 言いかけて、止める。（既定 0.5 はここ） |
| **開** | 0.70 – 1.00 | 下書きのまま喋る。取り消さない。 |

**何も選ばずに（全部送らない）進むと**: あかり 0.5−0.40=0.10（閉）／こはる 0.5−0.20=0.30（閉）／レイ 0.5−0.30=0.20（閉）。**全部「閉」**。逆に全部最大で選ぶと全部「開」。中間プレイは「半」に散る。設計意図どおり。

### 2.4 迷い秒数（`HesitationAt`）の使い方

**上げ下げには使わない。** 迷ったから偉い／ダメ、は作らない。迷いは優劣ではない。

代わりに、**【開き】の“確信度”**として、**ボスの台詞1行だけ**を変える。

```csharp
// その id で長く迷ったか（P2 の迷い秒数を基準にする＝E6 の対句と同じ流儀）
public bool Hesitated(string id) => HesitationAt(id) > HesitationAt("p2");
```

効き方: そのボスの【開き】を決めた**最も重い選択**（あかり＝`s1_4`／こはる＝`s2_4`／レイ＝`s3_5c`）で**長く迷っていたら**、改心シーンの冒頭にボスの1行が挿さる。

| ボス | 迷った場合に挿さる行 |
|---|---|
| あかり | 「……あのとき、すぐ決めなかったでしょ。……うん。それで、いい。」 |
| こはる | 「……迷ってくれたよね。あたし、それ、見てたよ。」 |
| レイ | 「……即答されたら、たぶん信じてなかった。」 |

**迷った＝軽く扱わなかった、の証拠として相手が受け取る。** 数値は動かない。台詞が1行増えるだけ。これが「迷ったことが何を意味するか」の答え。

## 3. プレイヤーへの見せ方

### 3.1 判断: 数値・バーとしては出さない。ただし3つの経路で必ず伝える

指揮官の意見（数値やバーで露骨に出すのは避けたい／だが伝わらないのは目的に反する）に同意する。設計者としての判断と根拠:

**出さない理由。** 【開き】をバーで出すと、プレイヤーは**メーターを上げるゲーム**を始める。そうなった瞬間、14か所の選択は「正解を選ぶ作業」に落ちる。本作の選択は「どちらも正しく、選ぶと何かを手放す」よう設計されている（`選択肢_リライトと提案:21-25`）。数値化はその設計を殺す。加えて、ミナは**他人を数える**存在であり、数えた結果をプレイヤーに開示しない（「集計だけ、しています」）のが一貫した態度。HUDに相手の心の数値が出るのは、この作品の礼儀に反する。

**では何で伝わるか。3経路すべてを実装する。**

### 3.2 経路1: スペル宣告カードの**技名**が変わる（最も強い伝達）

既存の `ApplySpell()`（`BossAkari.cs:77-84`）は `GetHud()?.AnnounceSpell(...)` で技名を画面中央に大きく出す。**ここが既に「ボスの心の状態を言葉で出す枠」になっている。**

`Spells[]` を **3段ぶん持つ**（閉／半／開）。技名がそのままボスの内面の言葉になる。

> 実装: `Spells` を `static readonly (...)[][] SpellsByBand`（3×4）にして、`ApplySpell()` の1行 `var s = Spells[_pattern % Spells.Length];` を `var s = SpellsByBand[(int)_band][_pattern % 4];` に替える。`_band` は `_Ready` で一度だけ `Openness3.Band(game.Openness("akari"))` から引く。**`ApplySpell()` は単一の差し替え点なので、ここ1か所で技名・弾色・HPバー色が全部追従する。**

### 3.3 経路2: HPバーの**縁**（`SetBossBarTint` の既存経路）

`ApplySpell()` は既に `GetHud()?.SetBossBarTint(s.tint)` でHPバーをスペル色に染めている（`BossAkari.cs:82`）。`Spells[]` が3段化すれば **`tint` も自動で3段になる**。追加実装ゼロ。

色の方針（`art-direction-v2` のアニメ塗り方針に沿う）:

- **【閉】** — 彩度を落とし、暗く寄せる。あかりなら現行 `6c9cd8` → `3e5878`。**濁って見える。**
- **【半】** — 現行のまま。
- **【開】** — 明度を上げ、わずかに暖色へ寄せる。あかりなら `6c9cd8` → `9fc4ea`。**透けて見える。**

**バーの形・長さ・本数は一切変えない**（難易度の指標であるHP本数と混同させない）。変わるのは色だけ。

### 3.4 経路3: RECLOSE の捨て台詞

`OnRecloseLine()`（`BossAkari.cs:496-500`）は、シールドを張り直すたびにボスの短い台詞を出す既存機構。`RecloseLines[]` を3段ぶん持つ。

**あかり:**

|---|---|---|
| 1 | 「既読も三秒でつけるし。返事も、すぐ書くし。……だから、ね?」 | 「……返事、遅くてもいいって、言われた。」 |
| 2 | 「バカ。……バカ、バカ。」 | 「……ごめん。いま、強がった。」 |
| 3 | 「……返して。読んだなら、返してよ。」 | 「……読んでくれて、ありがとう。」 |

> 【半】は現行のまま（現行の3行がちょうど「虚勢→弱気→最終形」の三段＝半開きの状態として完成している）。

### 3.5 伝わらない可能性への保険

初回プレイヤーは比較対象を持たないので「これが分岐した結果だ」とは気づかない。**それでよい。** 気づかせたいのは分岐の存在ではなく**目の前のボスがどういう人か**であり、それは技名と台詞で必ず伝わる。

ただし**2周目以降のために**、既存の `IsLineRead` / `MarkLineRead`（既読管理・`Epilogue.cs:302` 等）に技名を通しておけば、**前周と違う技名は「未読」として出る**。既読スキップが効かない＝プレイヤーは「あれ、前と違う」と手が止まる。これが最も自然な気づかせ方。追加実装は `AnnounceSpell` の呼び出し側で `MarkLineRead(s.name)` を1行呼ぶだけ。

## 4. 攻撃パターンへの効き方

### 4.1 難易度設計の原則: 総量を保ち、質を変える

**最重要の制約: 【開き】が低いプレイヤーが理不尽に詰まってはいけない。**

そこで**弾幕の総量（＝単位時間あたりの弾数）を3段でほぼ一定に保ち、分布を変える。**

| 段 | 手触り | 具体 |
|---|---|---|
| **【閉】** | **手数が多い。速い。隙が短い。でも単調。** 撃ち続けて止まらない人。 | 発射間隔 **×0.85**（速い）／1回の弾数 **×0.85**（1発あたりは少ない）／立ち位置の移動が少なく、**同じ場所から撃ち続ける**。 |
| **【半】** | 現行のまま。 | ×1.00 / ×1.00 |
| **【開】** | **手数が少ない。遅い。隙が長い。でも一発が広くて重い。** 言うべきことを選んで撃つ人。 | 発射間隔 **×1.20**（遅い）／1回の弾数 **×1.25**（一度に多い）／立ち位置がよく動き、**撃つ前に正面へ出てくる**。 |

**総弾数**: 閉 = 0.85÷0.85 = **1.00** / 開 = 1.25÷1.20 = **1.04**。ほぼ同じ。

**なぜこれが納得できるか（手触りの言語化）:**
- **閉じているボスは、こちらを見ていない。** だから同じ場所から同じ弾を延々撃つ。避け続ければ必ずパターンが読める。**苛烈だが、隙が分かりやすい**（＝指揮官の指定どおり）。
- **開いているボスは、こちらを見ている。** だから正面に出てきて、ため込んで、まとめて撃つ。**撃つ前に分かる＝避けられるが、一発が広いので位置取りが要る。**
- どちらも「難しい」が、**要求される技能が違う**（閉＝持久と反応／開＝予測と位置取り）。桜井的に言えばリスクとリターンの質が違うだけで、総量は等しい。

### 4.2 実装の当たり — 差し替え点は1つだけ

**`Enemy.cs:452-458` の `Di()` / `Dn()` が全ボス共通の既存スケール入口。** すべてのボスのすべての発射間隔・弾数がここを通っている（確認済み: `BossAkari.cs:368-371` の全 case、`FanDown`:390 の `Dn(_fanCount)` 等）。

ここに**係数を1つ掛けるだけ**で、3ボス全部の弾幕が【開き】に追従する。

```csharp
// Enemy.cs — 既存の2メソッドに、係数を1つ挟むだけ（新しい機構を作らない）
protected int Dn(int baseCount) =>
    Mathf.Max(1, Mathf.RoundToInt(
        (GetNodeOrNull<GameManager>("/root/Game")?.ScaleBullets(baseCount) ?? baseCount) * OpennessCountMul));

protected double Di(double baseInterval) =>
    baseInterval * (GetNodeOrNull<GameManager>("/root/Game")?.DanmakuIntervalMul ?? 1f) * OpennessIntervalMul;

// 派生ボスが OnEnemyReady で自分のボスIDから一度だけ引く（既定 1.0＝従来と完全に同じ挙動）。
protected float OpennessCountMul = 1f, OpennessIntervalMul = 1f;
```

**既定 1.0 なので、メーターを繋がないボス（`BossHikage`・中ボス・`BossMina`）は挙動が1ミリも変わらない。** 後方互換が自動。

立ち位置（§4.1 の「よく動く／動かない」）は `StanceOf(int pattern)` を `StanceOf(int pattern, Openness3 band)` に拡張して差し替える。これも `ApplySpell()` 内の1行から呼ばれるだけ（`BossAkari.cs:80`）。

### 4.4 ゲームデザイン面の懸念（`game-designer` に要確認）

設計者として自信がない点を明記する:

1. **`Dn()` の丸め**。`Mathf.RoundToInt` で弾数を ×0.85 すると、元が 3way のとき 3→2.55→**3**（変わらない）。小さい弾数のパターンで係数が効かない。**弾数の少ないパターンは個別に手当てが要る**（あかりの `AimedSpread` を 3way→1way にするのは `_aimedWing` を直接触る必要がある）。係数だけでは足りない箇所がある。
2. **難易度（Easy〜Lunatic）との乗算**。`Di()` には既に `DanmakuIntervalMul` が掛かっている。そこへ【開き】係数をさらに掛けるので、**Lunatic ×【閉】が想定外に厳しくなる可能性**がある。対策案: 【開き】係数の振れ幅を難易度が上がるほど圧縮する（Lunatic では ×0.92〜×1.10 に狭める）。**実測が要る。**
3. **総弾数を一定にしたが、体感difficultyが一定とは限らない。** 「狭い扇を速く」は「広い扇を遅く」より明確に難しい可能性がある。**プレイテストで閉／開の被弾率を実測して係数を調整する前提**とする。
4. **`BossMina`（FINAL）には【開き】を入れない。** FINAL は常にミナ本編固定（`StageMina.cs:79-82`）で、ミナは「相手」ではない。ここにメーターを入れると軸が二重になる。**FINAL の弾幕は現行のまま。**

## 5. エンディングへの合流

### 5.1 合流方式: メーターが「選べる選択肢」を決め、選ぶのはプレイヤー

指揮官の想定（**メーターが3択のうちどれを選べるかを決め、最後の選択でプレイヤーが選ぶ**）を採る。「メーターだけで自動決定」は手触りが弱いという判断にも同意する。

ただし**一点だけ変える**。「選べない選択肢を画面から消す」のではなく、**「選べない選択肢は画面に出るが、選ぶとミナが断る」**形にする。

**理由**: 選択肢が消えると、プレイヤーは**取り逃したことに気づけない**（出なかったものは見えない）。逆に、出ているのに選べないと、**何かが足りなかったことが分かる**。しかもその「足りなさ」は、ミナ本人の口から、責めない形で説明される。これは罰ではなく**情報**であり、2周目の動機になる。

### 5.2 3本のメーターを1つの結末にまとめる

```csharp
// 3人のうち、何人が【開】まで届いたか
public int OpenCount =>
    (Band(Openness("akari"))  == Openness3.Open ? 1 : 0)
  + (Band(Openness("koharu")) == Openness3.Open ? 1 : 0)
  + (Band(Openness("rei"))    == Openness3.Open ? 1 : 0);

// 3人のうち、何人が【閉】のままだったか
public int ClosedCount => /* 同様に Closed を数える */;
```

| 状態 | 選べるようになるもの | 意味 |
|---|---|---|
| **`OpenCount >= 2`** | **END A（送る）が選べる** | 三人のうち二人以上が本音を開いた。**ミナは「開くとどうなるか」を目の前で見た。**だから自分も開ける。 |
| **常に** | **END B（預かる）が選べる** | いつでも選べる。**何もしなくても選べる唯一の結末。** |
| **`ClosedCount >= 2`** | **END C（消す）が選べる** | 三人のうち二人以上が閉じたまま。**ミナは「開かないまま終わる」を目の前で見た。**だから自分も消せる。 |

**中間（開1・閉1・半1 など）は END B のみ。** これは罰ではない——**END B は3本の中で最も静かで、最も「何も起きない」結末**であり、中庸なプレイにちょうど見合う。

> **重要**: END A と END C は**同時に選べることもある**（例: あかり開・こはる開・レイ閉・…は `OpenCount=2` なので A が開く。`ClosedCount` が 2 に届けば C も）。実際には `OpenCount>=2` と `ClosedCount>=2` は3人では同時成立しない（2+2>3）ので、**A と C が同時に選べることはない**。常に「B のみ」か「A+B」か「B+C」の3パターン。**これが結果的に3本のエンディングの出し分けとして綺麗に閉じる。**

### 5.3 選べない選択肢を選んだとき（ミナが断る）

3択は**常に3つとも表示される**。選べない側を選ぶと、ミナが1行返して、**選択がもう一度出る**（`Final.cs:138-143` の `_refused` 機構＝既存の作法とまったく同じ）。

| 選んだ | 条件を満たさない場合のミナの返し |
|---|---|
| **送る**（`OpenCount < 2`） | 「……いいえ。……まだ、開いた方を、あまり存じ上げないので。」 |
| **消す**（`ClosedCount < 2`） | 「……いいえ。……消したら、どうなるか。……見ておりませんので。」 |

**どちらも「できない」と言わない。「知らない」と言う。** ミナは経験からしか学ばない存在で、三人を通してしか感情を獲得していない（メモリ [[mina-emotion-arc]]）。**見ていないことは、できない。** これが設定として一貫した断り方であり、同時にプレイヤーへの「何が足りなかったか」の説明になっている。

### 5.4 最終選択は何のためにあるか

メーターが結末を決めるなら最後の選択は何のためか——という指揮官の問いへの答え:

**メーターは「ミナに何ができるようになったか」を決める。最後の選択は「ミナに何をさせるか」を決める。** 前者は三人との関係の結果であり、後者はプレイヤーの意志。

だから **`OpenCount>=2` でも END B を選べる**のが肝。**開けるようになったミナに、開かせない自由がプレイヤーにある。** これが「メーターだけで自動的に決まる」を避ける本体であり、B案（道中は関係性に効き、最後に一度だけ決定的な選択が来る）そのものの形。

## 6. 3本のエンディングの定義

### 6.0 指揮官の当初案（送りだす／連れていく／下書きのまま）から変えた理由

**(1) 「三人を帰す／連れていく」はミナの持ち物ではない。** 三人は既に救出済みで、自分の明日を動かし始めている（`EndingFilm.cs:16-22`）。ミナが「帰す／連れていく」を選べる構図は、三人を**ミナの決断の目的語**に落とす。`maeda-pitfalls.md` P4（救う相手を器にしない・★最重要ガード）に抵触し、最優先テーマ（ヒロイン3人の闇の解消）を最後の一手で反故にする。**【開き】メーターを入れたことで、この危険はさらに高まった**——メーターがあると「三人を攻略して良い結末を買う」構図になりかねない。だから結末の対象は**ミナ自身**でなければならない。

**(2) 「外へ出る／残る」はこの作品のルールに無い。** 本作の空間は物理的な内外ではなく「送られたか／いないか」で分かれる（`Epilogue.cs:201-202`「光っていないほうは、観測できません。送られていないので」）。出入口は**送信**であり扉ではない。扉を作ると P3（設定で煽って描写で裏切る）。

**(3) 中核テーマが最後に一度も適用されない。** 全編は「他人の下書きをどうするか」を14回選ぶ話。最後は同じ問いが**ミナ自身の一件**に返るべき。

→ **3択を「ミナ自身の下書き1件をどうするか」に統一。** 指揮官案の C「下書きのまま」は END B としてそのまま生きている。A と B が「送る／消す」に置き換わった。**メーターは「三人がどう開いたか」を測り、それがミナ自身の開き方を決める**——この接続が、メーター追加後の設計の芯になる。

### 6.1 三本に共通する前提

PhGaze 19行を送り切った時点で四人は夜の空の下にいる。ここでミナが**初めて**「自分の下書きが一件ある」と言う。件数は1。宛先も本文も表示されない。**プレイヤーは最後まで、ミナが何を書いたかを読めない**（`maeda-lines.md` §3）。

> `s3_5c` で「見ています」を選んだ人には**2度目の遭遇**（`StageRei.cs:250`「それ、わたくしのです」）。`StageRei.cs:184` の設計コメント「効果＝E4 の開示に一行」は E4 が存在せず宙吊りだったが、**ここが正式な着地点**になる。

### 6.2 END A｜送る

**何が起きるか。** ミナが自分の下書きを送信する。送り先は明示されない。送信の直後、夜空の無数の光（＝他人の画面、`Epilogue.cs:200`）のうち**ひとつだけが新しく灯る**。ミナは初めて「観測される側」に回る。

**誰がどうなるか。**
- **ミナ**: 数える側から数えられる側へ。返事を待つ時間を持つ＝待たされる痛みも引き受ける。
- **あかり**: 一緒に待とうとする（`EndingFilm.cs:20`「ミナ。待っててくれて、ありがと」の反転＝今度はあかりが待つ側）。
- **こはる**: 「あと一行」を足した経験から、送った後の怖さだけを短く言う。
- **レイ**: 同接の数え方の話をもう一度。今度は数字が1。
- **少年（あなた）**: 何も送らない。プレイヤーは初めて**選択肢を渡されない側**になる。

**代償。** 「集計だけしています」と言って退がれなくなる。ミナの逃げ場だった一文が使えなくなる。

**最後の一行:** 「——ご主人様。……返事が、来るまで。……少し、こわいのですね。これは。」

### 6.3 END B｜預かる

**何が起きるか。** 送らない。棚に置いたままにする。**捨てもしない。** 三人はそれぞれの明日へ進み、ミナはその隣で数え続ける。何も劇的に起こらない——**起こらないことを、四人が選ぶ。**

**誰がどうなるか。**
- **ミナ**: 現状維持。ただし「自分の一件が棚にあることを、三人が知っている」状態に変わる。誰にも知られていなかったのとは違う。
- **あかり**: 急かさない。「いつでもいいよ」を、急かさない形で一度だけ。
- **こはる**: 自分が「あと一行」を足すのに何日かかったかを、数字で言う。
- **レイ**: 「わたしも、消さずに持ってるのある」と初めて自分から開示する。
- **少年（あなた）**: 隣にいるだけ。

**代償。** ミナの一件は最後まで開かない。プレイヤーは中身を永久に知らない。**三人の下書きは全部掘り起こしたのに、最後の一件だけが埋まったまま終わる。**

**最後の一行:** 「——ええ、ご主人様。まだ、下書きのままで。……急いでいないので。」

> 現行 END の最後の一行「——ええ、ご主人様。わたくしは、どこにも行きませんよ。」（`Epilogue.cs:267`）は**この END B の系譜**。`:164` の「END の一行は分岐しない」規約を**破る**のが本提案の本体なので、実装時はそのコメントも書き換えること（§7.4）。

### 6.4 END C｜消す

**何が起きるか。** ミナが自分の下書きを削除する。削除の瞬間、**同時に `ScatteredWords`（プレイヤーが全編で散らせてきた言葉）も棚から消える**。それまで一度も表示されなかった散った言葉の一覧が、**消えながら初めて画面に出る。**

**誰がどうなるか。**
- **ミナ**: 器が空く。次の声をいくらでも拾える状態に戻る。ただし三人に触れて得た「笑う・泣く」の出所——自分の一件——が無くなる。感情が消えるのではなく、**感情の根拠が消える。** 本人はそれを喪失として扱わない（扱えない）。
- **あかり**: 止めようとして、間に合わない。止めようとしたこと自体は残る。
- **こはる**: 何も言えない。
- **レイ**: 「それ、わたしがいちばんやったやつ」と、責めずに言う。
- **少年（あなた）**: 削除を止められない。

**代償（最重）。** 三人は無事。ミナだけが一段戻る。ただし**完全には戻らない——三人が覚えている。** これが救い。

**最後の一行:** 「——ゼロ件です、ご主人様。……あら。……なぜ、数えたのでしょう。」

> 最後の一行だけで、本人が処理しきれていないと分かる形にした（`maeda-lines.md` §6 遅延した理解）。「悲しい」と書かない。

### 6.5 `ScatteredWords` の活用（END C のみ）

`ScatteredWords`（`GameManager.cs:551`）は読み手ゼロの死にデータ。**一度も見せずに貯め続け、失われる瞬間に初めて全部見せる。**

- 削除処理が**棚全体**に及ぶ。
- `ScatteredWords` が出た順に降ってくる（最大 ~30件）。「傘、忘れてる」「もう送れない相手」「同接、9」——**全部プレイヤー自身が捨てた言葉。**
- 降りきると同時に消える。ミナは中身を読まない。**件数だけ言う。**

END A / B では一度も出ない（押しつけない）。既存提案 `選択肢_リライトと提案:48-56`（F4 の背景に降らせる案）とも両立する——F4 で一度降り、END C でもう一度、今度は消えるために降る。**二度目のほうが重い。**

**構造上の肝**: プレイヤーは14回、**他人**の下書きを判断してきた。その基準を全部ミナに適用すると「送る」。しかしミナ自身は何度も「急かしては、いません」（`StageKoharu.cs:180`）「どなたか、とは、伺いません」（`:171`）と**踏み込まないこと**を選んでいた。**ミナの流儀を尊重すると「預かる」、プレイヤーの流儀を通すと「送る」**——この齟齬が手を止める。「消す」は第三の軸＝ミナが繰り返した「自分のぶんは、自分で、拾っておきます」（`StageRei.cs:239`）の最終形。一番ミナらしく、一番救いがない。

## 10. 自己レビュー（`maeda-pitfalls.md` ゲート）

- **P1（型の焼き直し）** — 3ルートは別の型。A＝CARD5（観測する側からされる側へ）、B＝CARD3（アフターストーリー／何も起きない重さ）、C＝CARD7（自己を消して器に戻る）。3人のメーターも別々の意味（あかり＝返事／こはる＝弱さの開示／レイ＝数字）。
- **P2（主人公の受動性）** — 最終選択はプレイヤーの能動。加えて【開き】は「道中の選択が相手を変える」＝14か所すべてが能動の証跡になった。END A では選択後に**プレイヤーが何も送れない**時間を作り、待つ側に回らせる（意図的な受動の配置）。
- **P3（設定破り）** — 「送られていないものは観測できない」（`:202`）を全ルートで遵守。ミナの下書きの中身は3ルートとも最後まで非開示。扉・物理的な内外を作らなかった。【開き】は「本音を開いているか」＝既存の下書き／投稿のルールの内側にある概念で、新しい設定を足していない。
- **P4（相手を器にしない）★** — **メーター導入で最も危険になった箇所。** 対策を3つ打った: (a) **三人の「その後のタイムライン」を3ルート共通**にし、三人の明日がミナの決断にもメーターにも左右されない構造を担保（§8.4）。(b) **メーターは「好感度」ではなく「本人がどれだけ本音を開けているか」**＝三人の側の状態であって、プレイヤーへの好意ではない。(c) 【閉】のまま終わっても**三人は救われている**（改心シーンは必ず起きる。メーターは弾幕と台詞を変えるだけで、救済の成否は変えない）。**メーターを上げなくても三人は助かる**——これが器化を防ぐ最後の歯止め。
- **P5（泣きの押し付け）** — 感情語の直書きなし。END C の最後は「なぜ、数えたのでしょう」＝**本人が処理しきれていない**形で止め、悲しさを断定しない。トドメは各ルート1つずつ。メーターの数値をプレイヤーに見せない（§3）のも、感情の強制を避ける判断。
- **P6（伏線の畳み残し）** — `s3_5c`（ミナの下書き／着地点 E4 が消えていた）、`s2_4`（プレイヤー自身の画面）、`ScatteredWords`（読み手ゼロ）、`p4`・`s1_4`（フレーバー）を全部畳んだ。**14か所中12か所がメーターに接続**し、死に選択肢が消えた。新規の伏線は建てていない。
- **P7（エンジン再現性）** — 新規機構ゼロ。`ChoiceOverlay.Show`/`RecordChoice`/`ChosenAt`/`Enemy.Di()`/`Enemy.Dn()`/`ApplySpell()`/`AnnounceSpell()`/`SetBossBarTint()`/`OnRecloseLine()` すべて既存。`ArtRect` の `shot switch` を触らずに済むよう3ルートとも10カットに揃えた。**【開き】は永続化不要の純関数**（`_chosenById` から毎回計算）＝セーブ項目の追加ゼロ。
