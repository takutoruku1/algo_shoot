# design-gap — 設計書 ⇄ ゲーム実装 の乖離レポート

指定された設計書（シナリオ／ゲームデザイン文書）と、実際のゲーム実装（`src/*.cs`・`*.tscn`）を**Claude自身が読み比べて**乖離を洗い出し、マークダウンのレポートにまとめる skill。外部ツールは使わない。セリフは C# のソース内に配列／`T(...)` 呼び出しとして埋め込まれており、設計書の本文とほぼ一対一で対応する。

## 対象の決め方（どの設計書か）
1. ユーザーが引数でパスを渡したらそれ。
2. なければ IDE で開いているファイル（`docs/` 配下の `*設計書*` 等）。
3. それも無ければ `docs/` を見て候補を挙げ、ユーザーに確認する。

> 既定の対象は `docs/20260613/MINA_シナリオ設計書_v2.md`（本作の最新シナリオ設計書）。

## 変数
- プロジェクト: `d:\dev\algo_shoot`
- シーンチェーン（設計書のステージ構成と突き合わせる正準順）:
  `Prologue → Rei → Akari → Koharu → Final → Epilogue`（`res://*.tscn`）
- レポート出力先: **設計書と同じフォルダ**に `乖離レポート_<YYYYMMDD>.md`
  （例: `docs/20260613/乖離レポート_20260613.md`）。日付は `date +%Y%m%d` で取得。

## 設計書セクション → ゲーム実装 の対応表
セリフ照合はこの対応で行う。各 `src/*.cs` には `(int who, string text, string face)[]` 配列か
`T("話者","本文",...)` 形式でセリフが入っている（`who`: 0=少年 / 1=ミナ・地の文 / 2=ボス）。

| 設計書セクション | ゲーム実装ファイル | セリフの在り処 |
|---|---|---|
| [P-00] PROLOGUE 起動 | `src/Prologue.cs` | `_talk` の `T(...)` 群、ブートログ `boot[]`、`Acrostic[]`（4行英文） |
| [P-01a/b/c] STAGE3 レイ | `src/StageRei.cs` + `src/BossRei.cs` | ステージ進行は `Intro`/`BossIntro`/`Clear`、**ボスの改心かけあいは `BossRei.cs` の `Lines[]`** |
| [P-02a/b/c] STAGE1 あかり | `src/StageAkari.cs` + `src/BossAkari.cs` | 同上（改心セリフは `BossAkari.cs` の `Lines[]`） |
| [P-03] STAGE2 こはる | `src/StageKoharu.cs` + `src/BossKoharu.cs` | 同上（改心セリフは `BossKoharu.cs` の `Lines[]`） |
| [P-FINAL] FINAL 汚染 | `src/Final.cs` | `_talk` の `T(...)` 群、`Screams[]` |
| [P-EP] EPILOGUE 名前 | `src/Epilogue.cs` | `I(...)`/`O(...)` 群、`PwChoices[]`、`Acrostic[]` |
| 4. ステージ構成表（シーン順・舞台・道中の敵・ボス） | `*.tscn` + 上記各 `Stage*.cs` の遷移（`ChangeSceneToFile`）＋ `Background.cs` | シーンの有無・順序、`Rain()` 等の道中弾、ボスの種類 |
| 4-b. 汚染ゲージ（局面ごとの濁り） | `src/GameManager.cs`（汚染ゲージ）、`src/Player.cs`（`MurkTint`/汚染ティント）、`AkariRoot.cs`/`KoharuRoot.cs`（段階コメント）、`Final.cs`（黒く溶ける） | 各局面の濁り段階が実装に存在するか |
| 3. 登場人物（口調・一人称） | 全セリフ | ミナ一人称「わたくし」・口癖、少年「ぼく/きみ」等の一貫性 |
| ボス（穢れの核・倒さず届ける） | `src/BossRei.cs`/`BossAkari.cs`/`BossKoharu.cs` | 挙動。コード/コメントで判断、断定できなければ「要確認」 |

> 設計書がこの MINA 以外、または対応表が古い場合は、設計書中の特徴的なセリフを1〜2句 Grep（`src/` 配下）して対応ファイルを発見してから照合する。

## 乖離の種類（分類）
- **欠落**: 設計書にあるセリフ／場面／伏線／汚染段階が実装に無い。
- **改変**: 文言が違う（語句・語尾・句読点・英語引用のスペル）。原文と実装を併記する。
- **追加**: 設計書に無いセリフ／場面が実装にある（必ずしも悪ではない＝拡張。明記する）。
- **順序・話者違い**: 行順が違う／話者（少年⇔ミナ⇔ボス）が食い違う。
- **演出未反映**: 演出ト書き（例：BGMの間、白飛び、立ち絵の表情、机が天井へ落ちる等）が実装に見当たらない。**自動判定が難しいものは「要確認」**として落とす。
- **未確定項目**: 設計書自身が「仮」「未確定」と書いている箇所（例: EPILOGUEの仮PW）。乖離ではないが、実装が仮文のままかを付記。

## 重要度
- 🔴 **重大**: 物語の意味が変わる欠落・矛盾（伏線の仕込み/回収抜け、救済セリフの欠落、シーン欠落、話者違い）。
- 🟡 **軽微**: 語句・語尾・句読点・空白の差。意味は保たれる。
- ⚪ **要確認**: 演出ト書きなど、コードだけでは実装有無を断定しづらいもの。

## 手順

1. **対象設計書を確定**（上記「対象の決め方」）し、全文を Read する。

2. **対応表のゲームファイルを Read** する（必要分のみ。MINA なら
   `Prologue.cs` / `StageRei.cs` / `StageAkari.cs` / `StageKoharu.cs` / `Final.cs` / `Epilogue.cs`、
   構成・汚染確認に `GameManager.cs` / `Player.cs` / `AkariRoot.cs` / `KoharuRoot.cs`）。

3. **セリフ照合（章ごと）**: 設計書のテキストボックスを上から順に、実装の配列／`T(...)` と1対1で突き合わせる。
   - 全角／半角・三点リーダ（`…`/`……`）・ダッシュ（`—`/`——`）・引用符の差も拾うが、🟡軽微に分類。
   - 設計書の `【地】`/`【UI】`/`（中継・ミナの声で）` といった注記は、実装での扱い（地の文枠・UI表示・話者）と整合するか見る。
   - 実装側にだけある行は「追加」として記録。

4. **構成・遷移の照合**: シーンチェーンが設計書のステージ構成表（PROLOGUE→1→2→3→FINAL→EPILOGUE）と順序・有無で一致するか。各 `Stage*.cs` の `ChangeSceneToFile` の連鎖をたどる。道中の敵（言葉弾）・ボスの種類も確認。

5. **汚染ゲージの照合**: 設計書 4-b の各局面（PROLOGUE澄む→S1わずか→S2縁→S3深刻→FINAL黒く溶ける→帰還後）に対応する実装（`GameManager` の汚染値、`Player.MurkTint` の適用、各 Root のコメント段階、`Final.cs` の溶解）が存在するか。

6. **伏線の照合**: 設計書 8. 伏線対応表の ①〜⑤ について、**仕込み箇所と回収箇所の両方**のセリフ／演出が実装にあるか（例: ①＝Prologueの `Acrostic[]` と Epilogueの `Acrostic[]`／頭文字描画、③＝「ぼくの声じゃ、だめなんだ」、④＝「妹の様子でも、見ててくれ」）。

7. **未確定項目の確認**: 設計書末尾の「未確定項目」と実装の現況を突き合わせ、仮のままなら付記。

8. **レポート出力**: 下記フォーマットで `乖離レポート_<YYYYMMDD>.md` を Write（設計書と同じフォルダ）。最後にユーザーへ日本語で要約（重大件数・主な乖離・出力パス）を報告。乖離ゼロなら「設計書通り実装されている（軽微差のみ／全くなし）」と明言する。

## レポート フォーマット（出力する md の雛形）

```markdown
# 乖離レポート：<設計書名> ⇄ ゲーム実装
- 対象設計書: <相対パス>
- 照合日: <YYYY-MM-DD>
- 照合対象: <読んだ src ファイル一覧>

## サマリー
- 🔴 重大: N 件 / 🟡 軽微: N 件 / ⚪ 要確認: N 件
- 一言所見: <例：セリフはほぼ一致。演出ト書きの一部が未確認。>

## 🔴 重大な乖離
| # | 箇所(設計書) | 種類 | 設計書 | 実装 | ファイル:行 |
|---|---|---|---|---|---|
| 1 | [P-02b] | 欠落 | 「<原文>」 | （該当行なし） | src/StageAkari.cs |

## 🟡 軽微な差異
| # | 箇所 | 設計書 | 実装 | ファイル:行 |
|---|---|---|---|---|

## ⚪ 要確認（演出など自動判定困難）
- [P-00] BGMの明滅が「名前の由来」で止まる演出 … 実装で該当不明（Prologue.cs に間の制御見当たらず）

## 追加（設計書に無い実装）
- [P-01b] 「怖がらず、近づけ。…」少年 … チュートリアル目的の追加と思われる

## 汚染ゲージ
| 局面 | 設計書 | 実装状況 |
|---|---|---|

## 伏線 仕込み/回収
| 伏線 | 仕込み(実装) | 回収(実装) | 状態 |
|---|---|---|---|

## 未確定項目
- <設計書が「仮」とした箇所と実装の現況>
```

## コツ・注意
- セリフは**意味の同一性**を優先して判定する。句読点・記号差は拾うが🟡に落とし、🔴重大（欠落・話者違い・伏線抜け）と混ぜない。
- ファイル:行は実装側の根拠として必ず付ける（クリックできる）。
- 演出ト書きは過大評価しない。コードに痕跡（コメント・描画処理・フラグ）が見えるものだけ「実装あり」とし、見えなければ⚪要確認。憶測で「未実装」と断定しない。
- 設計書側が「仮」「未確定」と明記している箇所は乖離扱いにしない（未確定項目へ）。
- これは読解ベースの照合で、ビルドやゲーム起動は不要。挙動（ボスが本当に「倒さず届ける」になっているか等）まで確かめたい場合は `qa-autoplay` / `play-game` skill を併用する。
- レポートは上書き再生成してよい（同日なら同名）。日付違いは別ファイルになる。
